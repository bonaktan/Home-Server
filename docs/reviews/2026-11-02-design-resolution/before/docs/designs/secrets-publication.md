# Secrets publication and delivery decision

* **Date:** 2026-11-02
* **State:** D-24 selects Vault Community with local integrated storage, AWS KMS auto-unseal, and independently encrypted rebuild exports. SOPS/age and OpenBao remain alternatives; no automatic substitution is authorized. Feasibility is not yet proven.
* **Context:** [Approved requirements](../../concepts_brief.md), [Overview & Goals](../../design_draft.md), and the [shared-engine decision](database-boundaries.md).

## The decision

Choose between managing encrypted secret bundles through an admin-operated file workflow and running a secrets service with machine identities and an API. The online-service candidates are OpenBao and HashiCorp Vault Community. Every candidate must preserve off-site recovery before acknowledging changes, use existing application inputs, and leave activation under the ops admin's control. A particular product's ordinary Save button or local database write does not establish the required end-to-end durability.

The confirmed consumers are central services, ITskolar-System, an unnamed undeployed system, and some Pterodactyl workloads. Their applications and startup code must remain unchanged. No additional secrets service is installed on the second server; it remains an observability and backup-storage destination.

## Options

| | A — SOPS/age encrypted bundles | B — OpenBao static KV service plus protected publication |
| --- | --- | --- |
| Mechanism | Keep per-consumer encrypted, versioned bundles using SOPS/age. Publish protected recovery objects to R2 before reporting completion. A host/admin delivery operation decrypts only the selected consumer's active bundle into its existing configuration interface. | Run OpenBao static KV on the Atom, backed by a dedicated database/account in the selected shared PostgreSQL engine. Use the same protected off-site publication boundary for every acknowledged managed change; OpenBao provides the online read/identity/policy interface. |
| Administration | An operator edits and publishes bundles through one documented CLI workflow. There is no central web UI, online secret API, native per-request access policy service, or automatic credential leasing. | Native API, identity/policy controls, versioned KV, and an internal administrative UI. Ordinary business-secret writes must still go through the protected publisher; direct UI/CLI writes cannot be the normal completion path. Routine UI access can be read-only. |
| Delivery boundary | OS/deployment identities and separate bundle recipients restrict who can decrypt each consumer's values. Workloads receive their supported env/file inputs, not a universal decryption key. | Host/deployment identities receive scoped OpenBao read access. File rendering or an admin delivery step supplies existing env/file inputs. Workloads do not need an SDK, OpenBao token, or changed entrypoint. |
| Operating cost | No always-running secret server or additional database dependency. Operators manage recipient keys, version references, protected publication, and delivery permissions. | Operate an additional service, its internal TLS, policies, authentication/bootstrap, PostgreSQL dependency, seal/recovery material, upgrades, and recovery. Existing shared PostgreSQL does not eliminate this work or its resource usage. |
| Outage behavior | Already delivered inputs remain usable where the application permits. Published encrypted bundles can be delivered from an authorized local copy without a running secret server. New online fetches depend on OpenBao and PostgreSQL, unless an already authorized local delivery copy is available. New changes wait for off-site protection. |
| Principal benefit | A small operational surface matching manual activation and a limited host budget. | Central machine authorization and secret reads through a purpose-built service instead of distributing bundle decryption capability to delivery identities. |
| When it fails the requirement | An online secrets API/UI or centrally enforced per-read authorization is required; recipient separation or the operator publication procedure cannot be maintained; a consumer has no compatible existing input. | Direct native writes bypass protected publication; required recovery/bootstrap state is absent from protected recovery; shared PostgreSQL bootstrap is circular; the combined resource budget or a consumer integration does not pass validation. |

These are proposed mechanisms, not claims that a product natively implements the complete R2-before-acknowledgment workflow. The owner now prefers Vault Community, option C below, and requests immediate notice of problems. The comparison retains the alternatives and feasibility gates; product preference is not proof that the required operating workflow is complete. See [Vault operating considerations](vault-operations.md) for the current issues and pending operating-profile choice.

SOPS supports structured encrypted files including ENV/JSON/YAML and age recipients; it also has file/process delivery commands. Use it outside the application startup path here, rather than making an application run through a new wrapper. See [SOPS documentation](https://getsops.io/docs/) and [advanced usage](https://getsops.io/docs/usage/advanced/).

OpenBao provides versioned KV, scoped policy capabilities, and conditional writes. Its documented storage choices include PostgreSQL; its file-template agent can retrieve and render inputs. These features are components of option B, not proof of this design's publication guarantee. See [KV v2](https://openbao.org/docs/secrets/kv/kv-v2/), [storage configuration](https://openbao.org/docs/configuration/storage/), and [file templates](https://openbao.org/docs/agent-and-proxy/agent/template/). This proposal does not use its application process supervisor or automatic secret-triggered application restarts.

### C — HashiCorp Vault Community plus protected publication

The owner selected local integrated storage with AWS KMS auto-unseal and independent export-based recovery (D-24). Carry Vault forward and report concrete issues as they are identified; do not silently relax durability/delivery requirements or switch products. The [selected operating profile](vault-operations.md) makes clear that the second-server fallback rebuilds a fresh Vault rather than unlocking the original KMS-sealed store.

| Aspect | Proposed Vault approach and trade-off |
| --- | --- |
| Mechanism | Run a single Vault Community service with static KV v2 and local integrated storage on the Atom. This is an embedded backend, not a new PostgreSQL/MariaDB instance or a replica on the second server. Use the same protected publication/activation boundary below. |
| Administration and delivery | Provide the internal API/UI and scoped machine access through host/admin delivery operations. Keep application inputs and startup code unchanged. As with B, ordinary direct writes must not bypass protected publication; runtime apps do not need a Vault SDK or privileged token. |
| Operating cost | Maintain Vault, its internal TLS, access/authentication policy, seal/recovery material, integrated-storage files, upgrades, and tested restore/rebuild procedure. This avoids making online reads depend on shared PostgreSQL but introduces local Raft storage and its disk/I/O management. |
| Outage behavior | Already delivered inputs remain usable where the application permits. New online reads depend on Vault and its local storage; new managed changes wait for required off-site protection. Single-node operation provides no automatic failover, consistent with the accepted downtime policy. |
| Benefit | Uses HashiCorp's Vault implementation and its documented integrations. This can matter if existing operator knowledge or a required integration favors Vault; neither has yet been established as an owner requirement. |
| Failure conditions | A direct save or routine local snapshot is mistaken for protected off-site completion; integration or recovery material is missing; the single-node storage/combined host budget fails validation; or the chosen version/backend does not meet the required behavior. |

Vault documents [versioned static KV](https://developer.hashicorp.com/vault/docs/secrets/kv/kv-v2) and recommends [integrated storage for most use cases](https://developer.hashicorp.com/vault/docs/configuration/storage). PostgreSQL is also a documented, community-supported backend if the owner later wants a shared-PostgreSQL variant; that variant is not silently selected here. See [Vault PostgreSQL storage](https://developer.hashicorp.com/vault/docs/configuration/storage/postgresql).

### Why OpenBao and Vault both remain candidates

* **Licensing:** OpenBao's current source uses MPL 2.0. Vault's current source uses the Business Source License with an additional production-use grant that explicitly permits internal organizational use. Based on the described internal infrastructure, no licensing exclusion has been established for Vault; the owner has not required an MPL-only product. Confirm the selected release's actual terms before implementation. See the primary [OpenBao license](https://github.com/openbao/openbao/blob/main/LICENSE) and [Vault license](https://github.com/hashicorp/vault/blob/main/LICENSE).
* **Resources:** No comparative benchmark establishes that OpenBao is lighter or Vault cannot fit. HashiCorp's [integrated-storage reference architecture](https://developer.hashicorp.com/vault/tutorials/day-one-raft/raft-reference-architecture) targets production clusters and calls for workload-specific sizing; its small-cluster recommendations are not a measured minimum for this single-node home deployment. Apply the same combined-budget and recovery tests to both candidates.
* **Recovery:** Product-native local persistence, KV history, and periodic snapshots do not by themselves satisfy this plan's protected off-site acknowledgment boundary. This is a mechanism to verify for either product, rather than a reason to assume one meets it and the other cannot.
* **Storage variants:** Vault has a community-supported S3 backend with a configurable endpoint, providing an R2-backed variant worth testing if Vault is chosen. S3 API compatibility does not prove R2 compatibility for the selected version, safe retry behavior, or protected historical recovery. A mutable primary bucket and a retained recovery copy have different purposes; locking every primary object against overwrite/delete may break normal storage operations. Do not choose this variant or promise zero-loss recovery without those tests. See [Vault S3 storage](https://developer.hashicorp.com/vault/docs/configuration/storage/s3).

Options B and C provide similar capabilities needed here, but their exact features, backends, support, release behavior, and operational procedures are not assumed interchangeable. Vault is preferred by the owner; OpenBao has not been established as technically necessary or lighter.

## Required publication boundary for every option

Use one serialized admin publication path and standard encryption/object-storage/product tools. Any small orchestration must be limited to this operation, with explicit state and crash tests; do not build a general secret-management platform. The sequence below is a design contract to validate, not an implemented script.

1. **Prepare without activating.** Assign a stable request and bundle identifier. Capture the changed values, necessary metadata, previous version references, consumers, and recovery requirements in an encrypted candidate. Keep the current active inputs and upstream credentials intact. Include changes to recovery-critical configuration/keys in the protected scope, rather than protecting values alone.
2. **Protect the candidate and fallback copy.** Upload to a unique private R2 object key covered by the chosen retention protection. Use supported create-once/conditional semantics and verify the uploaded ciphertext and its identifying metadata through the direct authenticated storage API. For the selected D-24 profile, also copy and verify the complete independently decryptable encrypted candidate in the second-server recovery location. Keep Cloudflare retention administration and second-server retention/deletion authority separate from routine Atom credentials.
3. **Prepare the serving copy.** For A, validate the local encrypted bundle and recipient/delivery mapping. For B/C, import into a distinct staged KV location/version through the controlled identity and verify the recovered data matches the protected candidate without logging plaintext. An ordinary OpenBao/Vault write response is only an internal step; it is not the admin-facing publication acknowledgment.
4. **Protect the publication receipt.** Write a unique, retained receipt binding the operation, candidate digest, version identifiers, predecessor, and required recovery/configuration references. For D-24, verify matching complete receipts and their dependencies in both R2 and the second-server recovery location before reporting the change complete. Reconcile a partial receipt copy under the same request identity without early acknowledgment. A mutable local latest pointer must not be the only evidence that a version was acknowledged. Avoid secret-bearing metadata in object names and operational logs.
5. **Acknowledge publication, not activation.** The result identifies a protected pending version. Update the local catalog from the receipt; retain a recoverable history of acknowledged versions and protected active-version references. Concurrent writers must not silently fork the accepted history. Do not deliver pending values merely because they are the newest native KV/file version.
6. **Activate deliberately.** The ops admin selects the protected version, records recoverable activation intent, coordinates backend credential changes and supported delivery/recreation, validates the consumer, and records observed completion. Preserve previous values and compatible recovery references until revocation/retention policy permits removal. A crash after intent but before completion requires reconciliation; do not infer that the external credential or service changed atomically with a log record.

If any protection step is unavailable, leave the change pending/failed and preserve current active inputs. If an upload's result is ambiguous after a timeout, do not treat an immediate negative read as proof that it never committed: reconcile the same request/key, use supported conditional retry, and validate matching contents before reporting the result. Duplicate retries must not silently create conflicting versions or overwrite a protected object.

Cloudflare documents successful R2 writes after disk persistence, strong direct object operations, and atomic conditional writes. These support the proposed contract, while the client/retry/receipt implementation still needs proof. See [durability](https://developers.cloudflare.com/r2/reference/durability/) and [consistency, conditional operations, and in-flight writes](https://developers.cloudflare.com/r2/reference/consistency/).

Bucket locks can retain objects against overwrite/deletion, but a Cloudflare administrator can remove rules. Validate retention using the actual routine-host credentials and keep bucket management separate. Select retention so the last usable recovery set survives downtime; do not rely on automatic expiry of the only usable version. This does not promise survival of simultaneous compromise of every copy, recovery key, and administrative domain. See [R2 bucket locks](https://developers.cloudflare.com/r2/buckets/bucket-locks/).

For B/C, close alternative administrative write paths with product policy and operating permissions. Recovery-critical identity/policy/bootstrap changes need the same protected completion contract. Prove that a clean rebuild can recover acknowledged managed state from the off-site bundles/configuration and independent kit; an ordinary periodic database/storage backup must not create a secret-loss window. For B, bootstrap the PostgreSQL connection without first requiring the failed OpenBao service; for C, bootstrap/recover the selected integrated storage independently. Both require seal/recovery material outside the failed service. Internal authentication/session state that can be reissued must have an explicit rebuild procedure; no sole-copy credential needed for recovery may be dismissed as disposable.

## Delivery without application/startup-code changes

| Consumer | Planned integration boundary | Proof required before rollout |
| --- | --- | --- |
| Central Compose services | Supported secret files where the image reads them; otherwise a managed environment/configuration input supplied by the host deployment procedure. Keep credentials outside committed Compose/environment files. | Inventory each image's actual input interface and required bootstrap dependency. A Compose secret file does not automatically become an environment variable. |
| ITskolar-System | Preserve its existing environment-variable interface and Compose `env_file` usage. Deliver a selected active input set through protected host configuration and recreate the container under the admin's operational restart procedure. | Validate its existing input serialization/escaping, ownership and effective production Compose files, then actual database/application access. A simple Compose restart does not apply changed environment values. |
| Pterodactyl applications | Use supported panel environment/startup-configuration fields or an existing application configuration-file input, then restart through the panel/Wings lifecycle. Preserve startup commands, application source, images/eggs, and unrelated settings. Never replace a Wings-managed container through the infrastructure watcher. | Identify an actual relevant workload and installed panel/egg version. Confirm the application already consumes the intended variable/file and the existing deployment can supply it. Verify configuration retention and unrelated-value preservation before accepting this route. No generic wrapper or direct panel-database edit is assumed. |
| Unnamed planned system | Inventory its runtime/operator and existing inputs before enrollment. | A compatible interface and scoped delivery identity; do not silently identify it with Skybridge-Airways or promise an integration before its runtime is known. |

Docker documents Compose secrets as mounted files and says Compose restart does not apply environment changes: [secret delivery](https://docs.docker.com/compose/how-tos/use-secrets/) and [restart behavior](https://docs.docker.com/reference/cli/docker/compose/restart/).

The official Pterodactyl source exposes an application API route to update server startup/environment configuration, with validated environment and administrative fields. This is evidence for a candidate configuration boundary, not a verified integration with the deployed panel or an arbitrary egg. Read the existing complete configuration and preserve required fields; do not assume a one-key patch leaves every other variable unchanged. Any broad panel-admin API credential belongs only to the protected admin delivery operation, never to a workload. See the official [route](https://github.com/pterodactyl/panel/blob/1.0-develop/routes/api-application.php), [request validation](https://github.com/pterodactyl/panel/blob/1.0-develop/app/Http/Requests/Api/Application/Servers/UpdateServerStartupRequest.php), and [modification service](https://github.com/pterodactyl/panel/blob/1.0-develop/app/Services/Servers/StartupModificationService.php).

If a relevant application lacks a compatible existing input, record an integration blocker and return to the owner before changing that constraint. Do not describe a generic successful template/export as proof that the actual Pterodactyl consumer works. Any rendered or panel-stored plaintext remains sensitive runtime state; every choice requires access restrictions, safe backup/log handling, and cleanup. None hides delivered environment values from a fully privileged host administrator.

## Validation gates

Before the chosen mechanism is accepted for production, demonstrate these cases using harmless fixtures and isolated test consumers:

* Fail or interrupt each publication step, including after a successful upload whose response is lost. Reconcile/retry without false success, contradictory receipts, early activation, or loss of the previous version.
* Lose the local store and then both local machines. Using only the off-site copies and independent recovery kit, reconstruct the latest acknowledged managed version and metadata, an older working version, and active/intent state with any incomplete operation identified.
* Attempt routine-credential overwrite/delete of a retained recovery object; verify rejection and independently controlled retention administration. Test the configured expiry/pruning procedure without removing the last usable set.
* Exercise concurrent publication and activation versus an automatic image update. The update retains the explicitly active inputs or defers; a newly staged file/KV version does not become active accidentally.
* Deliver to an environment-only Compose consumer and an actual relevant Pterodactyl workload, restart through supported operations, and verify application access without source/startup changes or unrelated configuration loss.
* Verify per-consumer access rejection, marker absence from all new retained audit/log/spool/archive forms, delivered-file permissions, key/identity rotation, and bootstrap recovery without a running secret manager.
* Measure memory/disk/I/O, publication time, failure handling, and maintenance/rebuild peaks in the combined Atom budget. Published product features or an idle process are not capacity evidence.

## Other product considered

Infisical offers an online management interface, but its current published Compose minimum is 4 GB RAM for the application, PostgreSQL, and Redis together. That matches the Atom's entire nominal RAM before this server's other responsibilities. It is not included as an equally feasible option in this decision without a demonstrated combined budget; reusing shared dependencies alone does not establish fit. See [Infisical's deployment requirements](https://infisical.com/docs/self-hosting/deployment-options/docker-compose). This is a screening reason, not a measured claim that every smaller configuration must fail.
