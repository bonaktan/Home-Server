## Threats, planned boundaries and remaining proof

| Area | Security implication | Planned boundary and checks still required |
| --- | --- | --- |
| Shared host and Docker privileges | Vault shares the Atom with applications, Wings and monitoring. Host root or broad Docker control can inspect delivered credentials and alter services. Existing socket mounts, privileged containers and host filesystem mounts deserve direct review. A read-only bind of a Unix socket does not by itself restrict which API operations a permitted client can request. | Inventory each service's effective user/groups, capabilities, mounts, socket access, network and resource controls. Remove unnecessary privilege through supported configuration and verify the result. Do not claim Vault isolates secrets from the host administrator or hides a consumer's own credentials from that consumer. Docker explains the host-level authority of daemon control in its [socket protection guidance](https://docs.docker.com/engine/security/protect-access/). |
| Collaborator code and CI submission | Build scripts, Dockerfiles, dependencies and workflow edits can execute untrusted code. A job label or YAML conditional cannot make a broad production key safe. An approved malicious application can still misuse its runtime privileges and own credentials. | Treat the SSH key as permission to submit only; production independently validates owner authority, run/attempt, artifact/digest and target. Test leaked submission credentials, hostile input, symlinks, replay, reruns and substitution. Keep runtime secrets and host-controlled Compose out of build access; minimize token permissions and pin reviewed third-party Actions to immutable commits. [GitHub's secure-use guidance](https://docs.github.com/en/actions/reference/security/secure-use) describes repository-write/secret exposure, token scope and Action pinning. |
| Privileged operational scripts | The publisher, verifier and lifecycle executor are custom security-sensitive glue. A parsing, ownership, shell-expansion or crash-reconciliation mistake can bypass the intended policy even if Vault, SSH and Docker work correctly. | Review bounded request formats, strict identifiers, file ownership and atomic adoption, environment handling, no arbitrary evaluation, locks, durable state and failure recovery. Keep each operation narrow. Test the interfaces as an attacker with only the submission/workload identity. The conceptual design is not evidence these checks have been implemented. |
| Vault publication and KMS | Native KV success does not establish protected acknowledgment. An alternative write path could bypass recovery protection. Losing KMS can prevent unsealing the old store; exported values alone may omit bootstrap/policy/active-state dependencies. | Exercise every mutation route and every interrupted publication/activation boundary, including ambiguous successful uploads. Require complete verified candidates/receipts at both destinations before acknowledgment. Test rebuild with the original KMS unavailable and independent recovery material only. Recovery shares do not replace an unavailable auto-unseal provider; see [Vault seal behavior](https://developer.hashicorp.com/vault/docs/concepts/seal). |
| Backup compromise and retention | Routine host credentials must not remove historical recovery copies or their protection. Encryption alone does not stop poisoned uploads, exhaustion or R2 cost growth. Client timestamps do not establish a healthy set. | Preserve independent deletion/retention administration and test denial, interrupted relocking and isolated restores. D-32 selects advisory size alerts and explicitly accepts storage/cost exposure; do not claim hard admission or spending containment. R2/Restic compatibility remains a gate; see the [protection design](operations-tooling.md). |
| Continued writes without usable backup protection | The normal 24-hour database/Pterodactyl recovery-point target can be exceeded if writes continue and the active host fails before fresh protection returns. | D-30 explicitly keeps services running and alerts the owner, including both-destination failure with background/local writes. Persist state, retain last usable sets and clear only on fresh verified protection. New secret acknowledgment remains gated; central-alert interruptions remain accepted under D-20. |
| Delivered credentials and existing literals | Environment/file/panel delivery intentionally gives a consumer access to its own secrets. Existing checked-in credentials need coordinated replacement; removing a literal does not revoke a credential already copied elsewhere. Broad panel or provider admin tokens create wider exposure than a consumer-specific credential. | Use scoped per-consumer identities, restricted files and explicit active versions. Keep broad delivery/admin credentials out of workloads, build jobs and logs. Inventory existing exposure and rotate through protected publication/backend/consumer coordination. Do not rewrite repository history or rotate production credentials as an unannounced part of drafting. |
| Administrative and Vault audit | Raw arguments, headers, metadata, filenames and failure output can expose values. Forwarding-time redaction cannot undo a new local raw record. Native hashing and output suppression are not universal secret filters. | Prove harmless-marker absence across every newly retained form before enabling capture: native records, local files/journal, queues, rotations, archives and Loki. Record safe metadata and explicit coverage gaps. Check attribution, event loss and volume. Complete tamper-proof evidence after host-root compromise is not promised. |
| Networking and maintenance | A wrong bind, forwarding-header trust, Docker/Tailscale/IPv6 rule or staging override could expose internal administration/databases. Effective privileged rules remain an evidence gap. DHCP can interrupt recovery access. An image digest does not establish safety/compatibility. | D-29 uses the original TCP peer for internal authorization and confines replacement-address trust to actual ingress peers/public virtual hosts. Validate permitted LAN and denied forged-header/container/tunnel access. Preserve management recovery and one DHCP authority. Enforce release policy and real stateful recovery before replacement. |
| Second-host Loki authority | A permitted main-host principal can use broader backend APIs and may alter or interrupt second-host telemetry if compromised. Network source restriction alone is not query-only authorization. | D-33 explicitly accepts host-level Loki backend authority. Keep CI/unrelated principals excluded; add no query-only gateway for this purpose. This grants neither OS nor backup-retention administration. Validate allowed API behavior only in disposable fixtures and test rejected principals. |

## Security review before implementation

The completed dedicated security review used a fresh context, frozen target/supporting evidence and primary-document checks; its [complete report](../reviews/2026-11-02-security-review-rerun/security_report.md) and read manifest remain preserved. It confirmed the five existing Majors and added no distinct new finding. The later owner resolutions amend the plan; no new independent review of those edits is claimed.

Once Detailed Implementation exists, its separate readiness review must examine exact files, permissions, interfaces, migration order and test/recovery procedures. Reviews and accepted risks do not substitute for implementation tests or isolated restores. Keep distinction between a corrected document contract and a proven operating control. Resolve or explicitly decide any new material finding before the affected stage proceeds.

Detailed Implementation remains documentation: exact file changes, rationale, order, validation, stop conditions and recovery.
