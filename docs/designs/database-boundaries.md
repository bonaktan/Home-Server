# Database layout decision for the Technical Plan

* **Date:** 2026-11-02
* **State:** Owner selected A — shared engines, 2026-11-02 (D-22).
* **Context:** [Approved Overview & Goals](../../design_draft.md), especially G-02, G-05, G-11, and G-12.

## What the decision changes

The owner selected shared engines. Keep centrally operated PostgreSQL and MariaDB, with application-specific databases/accounts and explicit provisioning and migration ownership. Option B is retained below as the unselected alternative. Resource fit, supported migration privileges, adoption, and recovery tests remain required; selecting A does not establish that the existing provisioning is adequate.

Choose whether unrelated applications share a PostgreSQL/MariaDB engine process or each own a separate database container and volume. This determines administration, maintenance, resource budgets, deployment ownership, and recovery work. Both options keep database access internal and all central database infrastructure on the Atom; neither installs a database standby on the second server.

The current ITskolar failure does not establish that a shared process is unsuitable. The [read-only investigation](../investigations/2026-11-01-database-connectivity.md) verified working DNS/TCP, missing role passwords, missing CONNECT privileges, and absent expected schemas. A secret manager alone cannot repair those database-side conditions. A new container also needs correct initialization, credentials, permissions, schema, and consumer configuration.

## Two layouts

| | A — Shared engines, application-specific databases/accounts | B — Dedicated database containers per application |
| --- | --- | --- |
| Mechanism | Keep one centrally operated PostgreSQL service and one MariaDB service. Give unrelated applications separate databases and scoped identities; separate runtime access from provisioning and supported schema migration. | Put each application's required engine, volume, scoped identities, and private application network under that application's deployment lifecycle. Keep common operational standards for secrets, backups, observability, and recovery. |
| Administration | One repeatable onboarding procedure per engine manages the shared catalogs. Roles/account names must remain unique within their engine scope. App owners still own their supported schema migrations. | A repeatable application deployment pattern initializes/adopts its own database and accounts. This reduces shared-catalog coordination but creates more engine instances and independent administrative credentials. |
| Main benefit | Fewer engine instances and maintenance targets; avoids moving existing data solely to repair provisioning. | Application engine versions, restarts, and recovery can be scheduled separately. Engine-level mistakes or failures have a smaller application scope. |
| Main cost | Engine failure/restart/upgrade affects all consumers of that engine. Global roles, configuration, resource contention, and physical recovery are shared administration concerns. | More processes, caches, volumes, image/version records, backup checks, and update/recovery paths on the same 4 GiB host. Existing shared data must be adopted or transferred with verified recovery. |
| Migration impact | Preserve existing volumes/endpoints while inventorying state and fixing provisioning. Make production networking/configuration explicit before onboarding consumers. | Establish destination engines, compatible backups, account/schema state, and application-specific endpoints; validate restoration before switching consumers. Do not delete the old recovery source during adoption. |
| When it fails the requirements | Applications require incompatible engine versions/extensions, engine administrators must be independent, or shared resource/maintenance effects cannot be accepted or controlled. Incomplete grants remain a failure even when networking works. | The combined peak resource/storage budget does not fit, independent databases are omitted from backup/update inventory, or app ownership is mistaken for permission to give runtime code engine-admin access. |
| Remaining shared failure | The Atom, its storage, host administration, Docker daemon, and selected recovery dependencies. | The same Atom, storage, host administration, Docker daemon, and recovery dependencies. Additional containers do not create host or site independence. |

No extra memory estimate has been invented to make either layout pass. Separate instances normally require additional per-instance resources; that is a planning inference, not a measured capacity result for these workloads. PostgreSQL documents server buffer and workload memory settings in its [resource-consumption reference](https://www.postgresql.org/docs/18/runtime-config-resource.html). Test the selected layout alongside telemetry, secrets, audit collection, backups, and independent applications before rollout.

For shared PostgreSQL, separate databases still share cluster-level objects and administrative recovery concerns; PostgreSQL describes these boundaries in its [database-management overview](https://www.postgresql.org/docs/18/manage-ag-overview.html). For dedicated containers, retain ordinary least-privilege networking/mounts and avoid production Docker access from application jobs. Docker's [security documentation](https://docs.docker.com/engine/security/) explains the daemon's privileged relationship with the host.

## What improves account management in either layout

The operating procedure must take an application identity, database/engine, approved connection path, secret-version references, schema-migration owner, and required access as inputs. It produces verified database state and supported consumer configuration, not merely a SQL file that exited successfully. The exact automation tool is a separate Technical Plan choice.

1. **Inventory and adopt before writing.** Record exact existing database/account names, owners, grants, engine versions, schema/migration history, volumes, consumer locations, and recovery copies without publishing credentials. Preserve applied migration checksums; do not rewrite an already-applied Flyway migration to repair live state.
2. **Separate credentials and duties.** An admin/provisioning identity manages databases/accounts; the application's supported migration identity owns only its required schema work; runtime receives only needed access. Where an application's supported design combines runtime and migrations, document that concrete requirement instead of inventing an unsupported split. Do not distribute a shared engine superuser to consumers.
3. **Set actual backend credentials and privileges.** Coordinate the protected secret version with the persisted database account, connection privileges, schema/object permissions, and future-object grants where required. PostgreSQL password authentication fails when its role has a null password, and CONNECT is separately checked at connection startup. See [CREATE ROLE](https://www.postgresql.org/docs/18/sql-createrole.html) and [privileges](https://www.postgresql.org/docs/18/ddl-priv.html).
4. **Handle MariaDB's account identity explicitly.** Its account includes both user and host, and creation does not by itself grant privileges. An existing account must be deliberately adopted/altered: `CREATE USER IF NOT EXISTS` can return a warning without reconciling its state. See [MariaDB CREATE USER](https://mariadb.com/docs/server/reference/sql-statements/account-management-sql-statements/create-user).
5. **Treat first initialization and rotation differently.** Changing image initialization environment variables is not a reliable way to update accounts in existing persistent data. MariaDB documents that initialization variables generally do not change an already populated database directory in its [image environment reference](https://mariadb.com/docs/server/server-management/automated-mariadb-deployment-and-administration/docker-and-mariadb/mariadb-server-docker-official-image-environment-variables). Use an explicit supported adoption/rotation procedure; never delete a volume to make initialization rerun.
6. **Deliver and activate supported inputs.** Use existing application environment/file configuration. Preserve active versus pending secret inputs, coordinate database-side changes and manual admin recreation/restart, then revoke obsolete credentials through the agreed rotation procedure. Do not print passwords or put them into new command/audit records.
7. **Verify from the real consumer.** Check name resolution, TCP/TLS as applicable, authentication, database connection permission, required schema/migrations, and an allowed operation. Check that another application's data cannot be accessed. Preserve safe failure categories and record deployment/artifact/configuration identity.
8. **Validate recovery and repeat runs.** A second adoption/provisioning run must not erase data, recreate existing users unexpectedly, or reset credentials silently. Restore into an isolated target and verify application access with the matching secret/configuration set. A database health check alone does not establish consumer readiness.

The procedure and real-client checks address the confirmed account-management problems in either option. Layout selection decides the process boundary; it does not replace this procedure.
